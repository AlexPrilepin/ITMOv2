# Tree of Thoughts

- **Решение, для которого нужны альтернативы:** как реализовать защиту от утечки секретов в prompt перед отправкой в LLM (`SEC-1`).
- **Критерии выбора:**
  1. Соответствие правилу `SEC-1` (обязательно).
  2. Воспроизводимость проверки (есть конкретная команда).
  3. Стоимость поддержки (сколько кода/конфигов).
  4. Риск ложных срабатываний (не режет ли обычный код).

## Запрос

```text
Ниже контекст: сервис получает diff PR и отправляет его во внешний LLM.
Правило SEC-1: перед отправкой токены, пароли и приватные ключи удаляются.

Опиши три внешне разные стратегии реализации SEC-1:
A. регулярные выражения;
B. библиотека-детектор секретов;
C. явный allow-list (отправляем только код, комментарии и метаданные без значений строк).

Для каждой стратегии — плюсы, минусы и оценка по четырём критериям:
соответствие правилу, воспроизводимость проверки, стоимость поддержки,
риск ложных срабатываний.

Выбери одну и обоснуй. Не пиши код.
```

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| **A. Регулярные выражения** (`sk-`, `password=`, `PRIVATE KEY`) | Просто, быстро, минимум зависимостей | Пропускает нестандартные форматы, нужно постоянно обновлять паттерны | SEC-1: да; проверка: простая; стоимость: низкая; ложные срабатывания: средние |
| **B. Библиотека-детектор секретов** (например, `detect-secrets`) | Ловит много форматов, обновляется сообществом | Тяжёлая зависимость, нужна настройка под проект, медленнее | SEC-1: да; проверка: средняя; стоимость: высокая; ложные срабатывания: низкие |
| **C. Явный allow-list** — отправляем только код без значений строковых литералов | Жёсткая гарантия: секреты физически не могут уйти, потому что строки не отправляются | Модель теряет часть контекста, качество ревью может снизиться | SEC-1: да, максимально; проверка: простая; стоимость: низкая; ложные срабатывания: минимальные |

## Выбор

- **Выбранная альтернатива:** A (регулярные выражения) как первый шаг, с проверкой на регрессию из B (добавить `detect-secrets` как отдельный тест-сравнение). Вариант C отложен до отдельного решения, потому что снижает качество ответа модели.
- **Почему:** правило `SEC-1` требует удалить токены, пароли и ключи. Регулярные выражения покрывают типовые случаи и дают простую воспроизводимую проверку (см. `tests_unit.md` — `test_strip_secrets_before_llm`). Библиотека `detect-secrets` подключается как дополнительный тест-оракул: если regexp что-то пропустил, тест упадёт.
- **Как проверим:** unit-тест `test_strip_secrets_before_llm` — передаём diff со строкой `token = "sk-abc..."`, проверяем, что в prompt осталось `[REDACTED]`. Дополнительно — тест-сравнение с `detect-secrets` на наборе из 10 тестовых секретов.

## Что изменили в исходном артефакте

- **Файл и раздел:** `practices/practice_01/adr.md`, раздел «Рассмотренные альтернативы» и «Решение».
- **Изменение:** таблица альтернатив в ADR переписана по ToT-формату — три стратегии реализации `SEC-1` с критериями и обоснованием выбора, вместо плоского списка «rule-based / LLM без формата / LLM без санитизации». В разделе «Решение» зафиксировано: regexp как основная реализация, `detect-secrets` как тест-оракул, allow-list отклонён.
- **Как проверили:** сверили критерии с правилом `SEC-1` из `CASE.md`; проверили, что выбранная альтернатива имеет конкретную проверку в `tests_unit.md`.
- **Что отклонили:** альтернативу C (allow-list) — она гарантирует `SEC-1`, но снижает качество ревью, потому что модель не видит строковые литералы. Отклонение зафиксировано в ADR.

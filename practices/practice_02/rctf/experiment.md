# R.C.T.F.

- **Role:** помощник ревьюера backend PR. Анализирует diff и возвращает структурированный отчёт по правилам репозитория.
- **Context:** `TRAINING_PR.diff` + Context Pack из `practices/practice_01/context.md` (правила `SEC-1`, `API-1`, `REL-1`, `OUT-1`, `SCOPE-1`, `QA-1`, `OBS-1`, хорошие примеры для трёх правил).
- **Task:** вернуть краткое описание изменения, не более трёх рисков с `file:line` и evidence, список проверок. Если данных недостаточно — задать вопрос, а не выдумывать.
- **Format:** Markdown с разделами `## Краткое описание`, `## Риски`, `## Проверки`, `## Ограничения`.

## Полный запрос

```text
Role: помощник ревьюера backend PR. Анализируешь diff и возвращаешь структурированный отчёт.

Context: приложенный diff PR и Context Pack из context.md:
- правила SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1;
- формат риска: {file, line, evidence, risk};
- три хороших примера комментария (SEC-1, OUT-1, API-1).

Task: верни краткое описание изменения, не более трёх рисков, список проверок.
Если данных для риска не хватает — задай вопрос, не выдумывай.

Format: Markdown.
## Краткое описание
## Риски
1. file:line — нарушение (правило). Evidence. Проверка.
## Проверки
- пункт
## Ограничения
Не approve, не merge, не менять код.
```

**Приложен:** `TRAINING_PR.diff`.

## Что получили

```markdown
## Краткое описание

Добавлен `POST /api/reviews`, который принимает `payload["diff"]`, формирует промпт и вызывает `LLM.generate`, возвращая `{"comment": answer}`.

## Риски

1. `app/api.py:11` — `payload["diff"]` вызывает `KeyError`, если в теле запроса нет поля `diff`. Нарушает `API-1` (валидация запроса).
   Evidence: строка `return review_service.review(payload["diff"])` без `.get` и без валидации.
   Проверка: `POST /api/reviews` с телом `{}` → ожидать 422, не 500.

2. `app/review_service.py:12` — ответ возвращается как `{"comment": answer}` без полей `summary`, `risks`, `checks`. Нарушает `OUT-1`.
   Evidence: словарь с одним ключом `comment`.
   Проверка: `POST /api/reviews` с валидным diff → проверить наличие `summary`, `risks`, `checks` в ответе.

3. `app/review_service.py:11` — промпт формируется f-строкой без правил и без формата ответа. Модель может вернуть что угодно. Нарушает `OUT-1` (формат ответа) и `QA-1` (нет требования подтверждения риска).
   Evidence: `prompt = f"Review this pull request and find problems:\n{diff}"` без инструкций по формату.
   Проверка: сравнить ответ модели на один и тот же diff дважды — структура должна совпадать.

## Проверки

- Unit: `test_create_review_missing_diff` — POST `{}` → 422.
- Unit: `test_review_returns_structured_report` — есть `summary`, `risks`, `checks`.
- Integration: diff без правил в промпте → модель возвращает произвольный формат.

## Ограничения

Решение принимает человек. Помощник не approve, не merge, не меняет код (`SCOPE-1`).
```

## Что изменили в исходном артефакте

- **Файл и раздел:** `practices/practice_01/prompts.md`, раздел «Master Prompt v1» (шаги 1–4).
- **Изменение:** разделы master prompt переписаны в формате R.C.T.F. — явно выделены `Role`, `Context`, `Task`, `Format` с полным текстом запроса. Раньше это были общие заголовки «Цель и роль», «Входы и источники», «Задача и артефакты», «Формат результата» — теперь формат показан на конкретном запросе, который можно скопировать и использовать.
- **Как проверили:** прогнали запрос на `TRAINING_PR.diff`; ответ содержит ровно три риска с `file:line`, все подтверждены строками diff. Сравнили с P1-02 в `prompts.md` — формат совпадает, но R.C.T.F. делает его воспроизводимым без чтения остальных разделов.
- **Что отклонили:** предложение модели добавить в `Role` фразу «эксперт по безопасности уровня senior» — это не правило репозитория, а «усиление» роли, которое не влияет на результат. Отклонили как не подтверждённое требованиями.

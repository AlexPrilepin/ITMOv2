## Практика 5: Spec-Driven Development (OpenSpec + Spec Kit)

Сервис `ai-review-api` (помощник ревьюера PR) проведён через два SDD-фреймворка. Карта сдачи по критериям — `practices/practice_05/README.md`.

**OpenSpec (часть занятия).** Фича B (REL-1) прошла полный цикл explore → propose → review → update → apply → acceptance → sync → archive: timeout LLM → 504, ошибка LLM → 502, быстрый ответ без ожидания зависшего вызова. Правило `rules.design` (Mermaid) проверено на фрагменте до/после.

**Spec Kit (ДЗ).** Две «команды» в двух чатах написали спеки UI и логики. Сверка выявила 10 расхождений, они сведены в общий контракт `specs/review-api-contract.md`, спеки обновлены через `/speckit.clarify` до генерации кода. Реализованы страница `GET /` и логика: маскирование секретов до LLM (SEC-1), структурированный ответ (OUT-1), подтверждение рисков по замаскированному diff (QA-1, D7).

**Проверки.** `make check` — 42 теста. Сквозные проверки в Chromium — 22/22: успех, секрет, все коды ошибок, блокировка повторной отправки, лимит, очистка, приватность, XSS.

### Выводы

Самое ценное в Spec Kit оказалось не в шаблонах, а в шаге согласования. Каждая из двух спек по отдельности выглядела корректной, но вместе они давали утечку секрета в ответ API (D7). Без сверки это всплыло бы только после интеграции. OpenSpec заметно быстрее на точечном изменении существующего кода: delta-спеки и `archive` держат одну актуальную спеку, а CLI проверяет структуру без модели. Spec Kit больше даёт на новой фиче с несколькими сторонами, но требует больше контроля за агентом: длинные промпт-команды gpt-5 несколько раз «рассказывал», а не выполнял.

Главный урок — отчёт агента и его собственные тесты не являются проверкой. Утечки 7 форматов секретов, отсутствие сверки рисков с diff и ReDoS на строке в 20 000 символов нашли только независимое ревью, атакующие пробы и внимание к времени прогона тестов.

# Рефлексия: что согласовали и чему научились

> Составлено вместе с ассистентом (Claude) по фактам работы — коммиты, `docs/sdd/*`, журналы ревью в `specs/*/tasks.md`; выводы приняты студентом.

## Что согласовали

Две «команды» независимо написали спеки и разошлись в десяти местах (`specs/review-api-contract.md`, D1–D10): формат риска, тип `checks`, признак маскирования, тело ошибок, нумерация строк, отбор рисков, пустая сводка, метаданные, судьба поля `comment`. Самое ценное — D7: логика собиралась подтверждать цитату риска по **исходному** diff, а UI рассчитывал, что сервер уже всё замаскировал. По отдельности обе спеки выглядели корректно; при интеграции строка `API_TOKEN = "sk-live-…"` попала бы в ответ API и на страницу. Этот дефект виден только при сверке двух документов — ради этого шаг согласования и нужен.

## Чему научился

1. **Отчёт агента — не доказательство.** Пять раз агент сообщал о сделанном, а файла не было или отметки `[x]` отсутствовали. Проверял по `git status`, содержимому файлов и запуску тестов.
2. **Тесты автора повторяют его же код.** Тесты маскирования были зелёными, а 6 из 10 обычных форматов секретов (`DB_PASSWORD=`, `SECRET_KEY = "…"`, JSON `"password":`, `Bearer` в dict, PEM внутри строки) уходили в LLM. Нашлось только атакующими пробами независимого проверяющего.
3. **Время — тоже требование.** Набор тестов внезапно стал идти 78 с вместо 0,2 с — так нашёлся ReDoS: строка ровно в лимит API-1 обрабатывалась больше 10 минут до вызова LLM, и timeout REL-1 от этого не защищал. Без внимания к скорости прогона это ушло бы в код.
4. **TDD держится только под контролем.** Агент дважды писал реализацию раньше тестов, хотя правило было в `AGENTS.md`, конституции и промпте. Красная фаза видна в журнале hook (`docs/sdd/hook-runs.txt` — копия `logs/hook-runs.log`, который игнорируется git: FAIL → PASS).
5. **Порядок промптов влияет на результат.** В части 2 OpenSpec правило про Mermaid оказалось в том же сообщении, что и генерация design, и модель применила его заранее — сравнивать «до/после» было не с чем. Пришлось перегенерировать design в чистой сессии.
6. **Spec Kit и OpenSpec в одном репо не знают друг о друге** — после смены контракта принятая спека OpenSpec устарела, и никто этого не отметил (см. `06-comparison-openspec-speckit.md`).

## Где пришлось вмешаться человеку

Решения по 10 расхождениям контракта, остановка агента со сломанным venv (MSYS-Python вместо Windows-Python), три круга ревью логики, перегенерация фрагмента «до». Часть исправлений (ReDoS, детерминированный StubLLM, отметки задач) внёс проверяющий — отмечено в `specs/002-review-logic/tasks.md`; реализацию UI выполнил ассистент по `/speckit.implement`, пока студент был недоступен — отмечено в `specs/001-review-ui/tasks.md`.

## Что сделал бы иначе

- Сразу просить агента показывать `git status` после каждой команды Spec Kit — это сэкономило бы три круга «а файл-то не записан».
- Закладывать атакующие пробы и бюджет времени тестов в задачи с самого начала (`tasks.md`), а не находить их на ревью.
- Не держать два SDD-фреймворка в одном проекте без явного правила, какой из них ведёт контракт API.

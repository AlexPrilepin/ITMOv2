SDD 01 – Explore: Фича B (REL-1)

Что уже есть
- Валидация входа (Фича A, API-1) реализована в app/api.py:
  - 422 при отсутствии поля diff или при типе, отличном от строки.
  - 400 при пустом/пробельном diff.
  - 413 при длине diff > 20000; ровно 20000 принимается.
  - LLM не вызывается в случаях 1–3 (проверено тестами SpyLLM).
- Эндпоинты:
  - POST /api/reviews — возвращает dict {"comment": str}.
  - GET /health — возвращает {"status": "ok"}.
- Сервис и зависимости:
  - ReviewService.review формирует prompt и вызывает llm.generate.
  - StubLLM (app/dependencies.py) возвращает фиксированный ответ; сетевых вызовов нет.
- Глобальный handler RequestValidationError возвращает 422 {"error": "invalid request"} (не влияет на текущие тесты).

Спорно или лишнее
- Дублирование путей к 422: есть и явные ответы 422 в create_review, и общий RequestValidationError handler. Функционально не мешает, но сообщения об ошибках могут различаться.
- DIFF_LIMIT=20000 захардкожен в app/api.py. Это соответствует требованиям и тестам, но при изменении лимита потребуется правка константы в коде.
- Формат успешного ответа {"comment": ...} не совпадает с OUT-1 (summary/risks/checks), но это вне рамок текущей фичи B и существующих тестов.

Baseline проверок
- Выполненная команда: sh scripts/check.sh
- Результат: Ran 19 tests ... OK (все тесты зелёные на текущей базе).

Узкие границы для реализации фичи B (REL-1)
- Ограничивать только время выполнения внешнего вызова LLM (generate), не весь HTTP‑запрос.
- Таймаут по умолчанию 10 секунд; сделать конфигурируемым (для тестов значение можно уменьшить без влияния на прод).
- При превышении таймаута возвращать HTTP 504 с телом {"error": "llm_timeout"}.
- При любом другом исключении из LLM возвращать HTTP 502 с телом {"error": "llm_unavailable"}.
- Не допускать HTTP 500 и не включать трассировки стека в ответ; сценарии фичи A не изменяются.

Условия приёмки (что сохраняем)
1) Поведение фичи A (API-1) без изменений: статусы/сообщения 422/400/413, правило «ровно 20000 принимается», LLM не вызывается при невалидном входе.
2) Формат успешного ответа остаётся {"comment": ...} и текущие тесты tests/test_api.py и tests/test_review_service.py продолжают проходить.
3) Эндпоинт /health остаётся без изменений.
4) Не появляется новых логов/данных, нарушающих OBS-1 (никаких диффов/ответов модели в логах).

Вопросы к заказчику
- Где предпочтительнее задавать таймаут: как параметр ReviewService (инъекция через зависимости) или конфиг сервиса (например, переменная окружения LLM_TIMEOUT_SECONDS, по умолчанию 10)?
- Допускается ли использование ThreadPoolExecutor/конкурентного ожидания для таймаута (кросс‑платформенный способ для sync‑кода), или требуется иной механизм?
- Нужны ли дополнительные логи статуса/длительности (без диффа и ответа) при таймауте/ошибке для соответствия OBS-1, или оставляем логирование как сейчас?
- Требуется ли унифицировать сообщение 422 (например, однотипное {"error": "invalid request"}) или оставляем текущие тексты ошибок без изменений?

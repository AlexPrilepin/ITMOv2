# Сравнение OpenSpec 1.14.1 и Spec Kit 1.2.1 на одном проекте

Оба фреймворка применены к одному brownfield-сервису `ai-review-api`, один агент (OpenCode 2.0.20 + gpt-5), один день.

- **OpenSpec** — фича B (REL-1: timeout → 504, ошибка LLM → 502) полным циклом и правило `rules.design` (часть 2 практики): `docs/sdd/01–05`, `openspec/`.
- **Spec Kit** — ДЗ: две «команды» в двух чатах, спека UI (`specs/001-review-ui`) и спека логики (`specs/002-review-logic`: SEC-1, OUT-1, QA-1), общий контракт `specs/review-api-contract.md`.

## Как устроены

| | OpenSpec | Spec Kit |
|---|---|---|
| Единица работы | change: `openspec/changes/<имя>/` — proposal, delta-spec, design, tasks | feature: `specs/NNN-<имя>/` — spec, plan, research, data-model, contracts, quickstart, tasks |
| Спецификация | delta к «живой» спеке по capability: `## ADDED/MODIFIED Requirements`, сценарии WHEN/THEN | полная спека фичи по шаблону: user stories с приоритетами P1–P3 и Given/When/Then, FR-…, измеримые SC-…, Assumptions |
| После реализации | `sync` + `archive`: delta вливается в `openspec/specs/<capability>/spec.md`, change уходит в архив | спека остаётся в каталоге фичи; общей «текущей» спеки системы нет |
| Правила проекта | `openspec/config.yaml`: `rules` по артефактам (проверено: Mermaid в design) | `.specify/memory/constitution.md`: принципы, Constitution Check в plan |
| Детерминированная проверка | CLI: `openspec validate --strict`, `list`, `show`, `instructions` (без LLM) | нет валидатора; качество — через `/speckit.checklist`, `/speckit.analyze` (LLM) |
| Неясности | вопросы агента в explore, решения человека в propose/update | маркеры `[NEEDS CLARIFICATION]` (≤ 3) и `/speckit.clarify` с разделом Clarifications |
| Состояние | всё в файлах change | общий указатель `.specify/feature.json` — параллельные сессии мешают друг другу; обход — `SPECIFY_FEATURE_DIRECTORY` |

## Что получилось на практике

| Наблюдение | OpenSpec | Spec Kit |
|---|---|---|
| Время цикла | ≈ 30 мин (explore → archive), 1 круг ревью | ≈ 3 ч (constitution → implement двух фич), 3 круга ревью логики |
| Сбои агента при выполнении команд | 1: патч со строками `-` вместо `+` (поймано до подтверждения) | 5: дважды результат только в чат без записи файла (конституция, спека UI), один раз `tasks.md` не создан, спека логики мимо шаблона, дважды заявлены отметки `[x]`, которых в файле не было |
| Что нашло ревью | R1 — `with ThreadPoolExecutor` ждал бы зависший LLM, 504 не пришёл бы вовремя | D7 — секрет из исходного diff попал бы в `proof` ответа (видно только при сверке двух спек); R1/R6 — 7 форматов секретов уходили в LLM; R2 — QA-1 не сверял риски с diff; R7 — секрет из ответа модели в title/summary; R8 — ReDoS: строка в 20 000 символов > 600 с |
| Тесты | 19 → 23 | 23 → 42 unit + 22 сквозных в браузере |

Почему у Spec Kit больше сбоев: его команды — длинные промпт-шаблоны, которые агент должен исполнить сам (создать каталог, скопировать шаблон, заполнить, записать `feature.json`). Команды OpenSpec короче и опираются на CLI (`openspec instructions … --json`, `validate`), часть работы делает детерминированная программа. Чем больше шагов отдано модели, тем чаще она «рассказывает» вместо того, чтобы делать.

## Расхождение двух фреймворков в одном репо

Принятая спека OpenSpec `llm-dependency-errors` фиксирует сценарий «успех → 200 `{"comment": …}`», а контракт Spec Kit (D10) заменил формат успеха на `summary/risks/checks/secrets_masked`. Ни один инструмент этого не заметил: у них разные каталоги и нет общей модели системы. Правильный путь — отдельный change OpenSpec с `MODIFIED Requirements` или выбор одного фреймворка на проект.

## Когда что брать

- **OpenSpec** — небольшие изменения существующей системы: delta-спеки и `archive` поддерживают актуальную спеку по capability, CLI проверяет структуру без модели.
- **Spec Kit** — новая фича, где важны приоритеты историй, измеримые критерии и план с исследованием; хорошо ложится на работу нескольких сторон, если вручную добавить общий контракт (встроенного механизма нет).
- В обоих случаях отчёт агента не заменяет проверку: файлы, тесты и атакующие пробы нужно смотреть самому.
